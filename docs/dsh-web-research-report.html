dsh-web-research — What it does & how it flows

A DeepSeek Harness Host plugin that ports the Hermes-agent web-research plugin: a local, open-source-first web search and extract pipeline (Hister archive cache + SearXNG live search + wreq TLS-fingerprint fetcher with Camofox browser fallback), exposed to agents as three tools and two optional ctx.web seam providers.

1. What this thing is, in one paragraph

dsh-web-research gives DeepSeek Harness agents a private, inspectable, disk-backed web research subsystem. Instead of calling an external search API, it drives local components that the Hermes project already built:

  • Hister — a local archive server storing every ingested page; it also extracts clean text from raw HTML/PDF server-side, so the pipeline stores raw HTML once and re-reads cleaned text on demand.
  • SearXNG — a meta-search engine JSON endpoint used only for discovery (URLs + snippets, never citable).
  • wreq — a TLS-fingerprint-rotating HTTP client (separate venv) that fetches pages without looking bot-like.
  • Camofox — an anti-detect headless browser (REST :9377) used as a fallback for JS-required or Cloudflare-challenged pages.

The Node host plugin (main.js) registers three agent tools — web_recall, web_research, web_read — each of which spawns the Python pipeline (python/webresearch/cli.py) as a subprocess: one JSON object on stdin, one JSON document on stdout. All backend settings come from a gitignored .env through the WEBRESEARCH_* / CAMOFOX_* contract, so an existing Hermes environment works unchanged.

2. Architecture flow — how the pieces are wired

Figure 1 — Deployment & wiring: the patch row imports main.js into the live host; tools/seam/systemPrompt are registered against the host context; every tool call crosses the host↔subprocess boundary.

Key boundary: the Node side never touches the web. All HTTP and subprocess work happens in the Python pipeline; main.js only resolves config, spawns cli.py, and relays one JSON document back. This keeps the plugin dependency-free on both sides (Node built-ins; Python stdlib urllib/subprocess).

4. Flow — the web_research stage pipeline

9. Data contracts

stdin (host → pipeline)One JSON object per call, e.g. {"query":"…","fetch_top":3,"limit":10}. cli.py forwards only keys the target function accepts (schema additions degrade gracefully).
stdout (pipeline → host)One JSON document: {results:[…], diagnostics:{…}} or {error, diagnostics}, or the seam shapes for search_meta/refresh_doc. Valid JSON + exit 0 → tool result, even when it contains an error.
Exit codes0 pipeline ran; 1 invocation-level error; 2 unknown command or bad stdin args. Nonzero → the host rejects with the first 600 chars of stderr.
Result rows{url, title, text, source?, retrieved_at?} — text is always clean text re-read from Hister. source ∈ cache | fresh | updated | cache-stale (web_research), or wreq | camofox (refresh_doc).
diagnosticsPer-source counts (searxng, hister, cached, fetched, ingested), failed[] with stage/url/reason, spam_filtered, reranked, diversity_overflow, elapsed_s, freshness mapping.
LogsStructured lines to $WEBRESEARCH_LOGS_DIR or ~/.dsh/logs/web-research.log — every stage, retry, fallback, and failure with timestamps.

10. Failure handling & quality gates (the design spine)

Resilience rules

  • Stage contract: a stage returns a typed result or raises — it never silently returns empty. The caller owns retry/fallback/logging.
  • Bounded retries everywhere: retry() with exponential backoff (2 attempts for searches/fetches/ingests, 3 for document reads); RetryExhausted for loops.
  • Parallel discovery with isolation: SearXNG failure or Hister failure never aborts web_research — each is reported in diagnostics.failed[].
  • Per-hit isolation in recall: one broken document doesn’t sink the whole web_recall.
  • Stale-doc grace: an old cached copy is better than nothing — stale hits that fail re-fetch fall back to source:"cache-stale"; brand-new URLs just get dropped with a diagnostic.
  • Never cache or serve a failure shell: _looks_like_failure() rejects short/empty/JS-required/cookie-wall text at classification time, after wreq, and after camofox; a cached shell is force-refreshed.
  • Toolbounding: subprocess timeout 240 s with SIGKILL, abort-signal wiring, JSON validation on stdout. A poisoned page can’t hang the agent.

Quality gates

  • Spam/mirror filter (filter_spam): registrable-domain eTLD+1 heuristic (stdlib-only, no publicsuffix dep); seed blocklist of Stack Overflow mirrors + SEO-scraper farms; operator WEBRESEARCH_BLOCKED_DOMAINS extends; WEBRESEARCH_ALLOWED_DOMAINS always wins; explicit site: or include_domains queries bypass both (a constrained search is already deliberate).
  • Diversification (diversify): ≤ 2 rows per registrable domain, overflow moved behind the diverse head in first-seen order — results are capped, never truncated.
  • Citable-text policy: only Hister-derived clean text is returned with a text field; search-engine snippets are discovery hints only (and web_search_core tells the agent to answer only from entries carrying text).
  • Optional rerank that “never fails the tool”: unconfigured or broken rerank endpoints are logged and bypassed.

11. End-to-end narrative — one research question

Concrete walk-through of everything touching at runtime. Say the agent needs recent information on a topic:

  1. The agent calls web_research(query, fetch_top=3, limit=10). Host validates args; main.js builds the child env from config precedence and spawns python3 …/cli.py research, writing the args JSON to stdin (Figure 2).
  2. In parallel, core.py queries SearXNG (live discovery) and Hister (cached recall), applies the spam filter to the live feed, then unions and dedupes by URL (Figure 3, stages 1–2).
  3. Each recalled URL is classified against cache freshness: fresh hits are served straight from /api/document; stale hits and uncached URLs form a bounded refresh queue, stale first (stage 3).
  4. Up to fetch_top URLs go through _refresh_doc(): fetch_html() tries the wreq venv with fingerprint rotation (PDFs take the raw-bytes path), falls back to a Camofox browser render, ingests the HTML/PDF into Hister (CSRF handshake for /api/add), re-reads clean text, and runs the failure-shell gate — escalating to a browser render when wreq’s cleaned text looks like a JS-required shell (Figures 4–5).
  5. Results accumulate with provenance (cache | fresh | updated | cache-stale); the optional reranker reorders by relevance; diversification caps domain repetition; the JSON document (results + diagnostics) lands on stdout.
  6. main.js parses it, returns it to the agent, and the same document is logged to ~/.dsh/logs/web-research.log. The next time any tool asks about the same pages, they are served from the Hister archive — the pipeline got cheaper and more private with use.

The same choreography, minus the live-search stages, is what web_read (single URL, cache-first) and web_recall (cache-only) run; and the whole thing is reachable from the built-in web_search/web_fetch tools through the ctx.web seam providers when the profile points the web row at them (§7).
